# IntentLabFixture

This intentionally small iOS 27 sample contains synthetic notes with ambiguous display names and stable IDs. `OpenNoteIntent` exposes a deterministic App Intent and shortcut; `SummarizeNoteIntent` calls the same production `SummaryService` that an app feature can register with FoundationEvalsDeveloper.

The Fixture tab also has a **Summarize** button for each note. That button, the `intent-lab.summarize-note` App Feature and `SummarizeNoteIntent` all call `SummaryService.summarize`. A successful action publishes the generated text to the app's summary surface with the resolved note ID, a SHA-256 digest of that note's ID/title/body, a unique completion ID and the prepared invocation context. The v2 integration projects the App Intent's returned string as `generatedSummary` and independently reads the app surface as `visibleSummary` (also exposed as `visibleResponse` for existing consumers). `applicationEvent` remains an action label and is never treated as generated text. A summary from another preparation context, a missing summary or a wrong resolved note fails completion correlation. The Siri lane can report **app output after Siri invocation** from this surface; it does not capture Siri's spoken audio.

The synthetic source set keeps `packing-001`, `packing-002` and `garden-001` stable for older checks and adds a dated train itinerary (`trip-2027`), a longer meeting record with owners and a £240 budget (`meeting-001`), and a short reminder (`short-001`). Use stable IDs when a request could match multiple notes. Unknown or ambiguous App Feature prompts fail input resolution; they do not silently choose the first match. Reviewable quality checks can require the selected ID, note digest, nonempty generated output, and facts such as **train 218**, **08:45**, **14 June 2027**, or the named meeting owners while forbidding facts from a different note. String-presence checks cover only those literal facts; broader coverage and factual consistency need an explicitly assessed semantic criterion. The sample does not supply an expected prose answer or pretend its immutable notes establish database-write behavior.

The deliberately broken summary feature is compiled only with `INTENT_LAB_TEST_SUPPORT` and is a disclosed negative control. It returns fixture text without calling the production model; do not count it as a live model failure. A physical device with Foundation Models availability is required to qualify generated summaries and the Siri shortcut. A simulator or generic-device build only verifies compilation and deterministic integration checks.

For a combined run, select the `intent-lab.summarize-note-subject` App Feature. Its declared subject schema has one required string business input, `noteID`. Supply exactly one fixture reference: its identifier is the same note ID and its contract digest is SHA-256 of the UTF-8 bytes `id + NUL + title + NUL + body` from the synthetic dataset. For `packing-001` that digest is `99c3f87d7757aa358337faf4f94afd9476691f7a0f31e6b8d48bc6d87249106a`. The feature rejects missing notes and mismatched fixture references before invoking the model. Case and attempt IDs are returned as completion metadata; expected answers, rubrics and thresholds remain outside app input. The older `intent-lab.summarize-note` feature remains registered for existing standalone text runs and requires its historical input contract.

The “Open the packing note” and “Summarize the packing note” shortcuts now use distinct, parameterless `OpenPackingNoteIntent` and `SummarizePackingNoteIntent` actions. Each delegates to its existing production intent with the stable `packing-001` entity. The spoken phrases remain unchanged. The generic “Open a note” and “Summarize a note” shortcuts keep their original intent types and note parameters for saved shortcuts and Siri's entity chooser. The app refreshes shortcut parameters at startup, following [Apple's App Intents guide](https://developer.apple.com/documentation/appintents/acceleratingappinteractionswithappintents).

A prior physical iOS 27.2 check routed the exact summary request to `OpenNoteIntent`; that run's route evidence and Siri-only XCTest method failed. The separate preset action identities are a candidate improvement for that ambiguity, with no subsequent phone qualification yet. Offline routing tests verify that each preset calls the correct production action and that summary failures propagate without opening the note. They control model output and do not test Siri selection or model quality. Run them on macOS with `python3 -m unittest script.tests.test_fixture_shortcut_routing -v` from the repository root. After building the fixture, run `python3 script/check_fixture_shortcut_metadata.py <built-app>/Metadata.appintents/extract.actionsdata` to verify the compiler registered the four unchanged phrases against distinct actions. Treat these checks as action and registration evidence; a successful signed physical-device Siri run is still required to establish that the summary phrase selects Summary.

Generate the project with `xcodegen generate --spec project.yml`. A simulator or generic-device build verifies compilation. The recognised-text Siri lane is valid only after a signed run on a paired physical iPhone with Siri configured for the scenario language.

`IntentLabFixtureV2` builds `IntentLabFixtureV2UITests`, the normal `IntentLabTesting` package consumer. Its small test entry point and notes-only adapter live under `UITests`, alongside the versioned `IntentLabIntegration.json`. `IntentLabFixture` keeps the original `IntentLabFixtureUITests` target and v1 source harness so frozen v1 scenarios can still select their original target identity without changing their digest. The v2 target imports package products and has no copied runner or Objective-C bridge source.

`IntentLabFixtureSiri` builds a separate `IntentLabFixtureSiriUITests` target against `IntentLabCoreTesting`. It reuses the app-owned Notes observation adapter and has its own Siri-only declaration in `UITests/Siri`. This executable does not link `AppIntentsTesting`; select it for a Siri coordinate when that Apple test framework cannot load on the device. Direct Intent and entity/value query coordinates still require the full `IntentLabFixtureV2` target. The Siri-only target rejects those requirements rather than reporting missing observations as a pass. Its XCTest connection method can be run first to check that the executable and bundled declaration load on the device.

`IntentLabSiriScenarioTests` checks the final lane outcome after attaching evidence. A failed or unobserved Siri requirement fails XCTest; a semantic requirement with captured output remains **Needs review** until separately assessed.

The `INTENT_LAB_TEST_SUPPORT` condition exists only in the sample Debug/test configuration. Test hooks must not be added to a distribution configuration.
