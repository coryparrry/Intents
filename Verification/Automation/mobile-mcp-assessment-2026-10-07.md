# Mobile MCP assessment — 2026-10-07

## Decision

Mobile MCP is a plausible **development-only UI inspection/input aid**, but it does not unblock the current failing iPhone path. Do not add it to the shipped Intents stack. A separate local, version-pinned experiment on a disposable simulator could help inspect/tap the setup UI; it cannot create the two-owner qualification evidence, release the existing Intents controller lease, repair Apple's `AppIntentsTesting` load failure, or prove the post-run readback. Running its Device Kit/XCUITest agent on the same device during an Intents test would introduce another controller/runner owner into the workflow that is explicitly built around exclusive ownership and cleanup.

## What it actually needs

- It is a local Node MCP server. First use of `npx` needs npm registry/network access unless the matching packages are already cached. The package lock contains a prebuilt platform-specific mobilecli binary; no separate global mobilecli install is needed. README documents Xcode/command-line tools and a booted simulator for iOS simulator use.
- The current README/roadmap say iOS simulator and real-device automation use the project's Device Kit, and that `go-ios` was removed on 2026-09-04. For a real iPhone, mobilecli documents agent installation with a provisioning profile; this remains a locally signed/provisioned XCUITest runner workflow. DeviceKit iOS itself documents an XCUITest server, build artifacts, and local HTTP/JSON-RPC control. Thus physical use still needs device trust, a compatible Xcode/toolchain and provisioning/signing; it is not an offline/no-install path.
- Current `mobile-mcp` README documents anonymous PostHog/Scarf telemetry and an opt-out (`MOBILEMCP_DISABLE_TELEMETRY=1`). It exposes app install/uninstall, launch/terminate, device input, clipboard, logs, and screenshots, so it has broad local-device authority. Pinning a version and disabling telemetry would be necessary for a bounded experiment.
- The wiki page [Getting Started with iOS Real Device](https://github.com/mobile-next/mobile-mcp/wiki/Getting-Started-with-iOS-Real-Device) is stale: it still instructs global `go-ios`, WebDriverAgent cloning, tunnels, port forwarding, and signing WDA. Do not use it as the current setup guide. The current README and roadmap describe the newer Device Kit/mobilecli route. `MOBILEMCP_LEGACY_ROBOT=1` explicitly opts physical iOS back into the legacy robot path.

## Fit to the stalled Intents workflow

Mobile MCP can observe and operate native app screens using accessibility snapshots, screenshots, taps, typing and batched actions. This may help a human/developer explore setup screens on an isolated simulator. Its generic UI actions do not independently establish the selected owner and protected owner, verified subject identity, deterministic released state, durable receipt, or correct-record readback required by the Intents M3 contract. It also cannot fix the observed Apple framework ABI error before the test bundle loads.

Local evidence reviewed:

- `Verification/Automation/ACCEPTANCE.md` says actual two-owner setup/query/subject/readback and two matching live setup paths remain unqualified; the current evidence supports no qualified two-owner workflow.
- `Verification/Automation/physical-siri-qualification-1.json` records the target iPhone UDID `00008140-000E4D803C0B001C`, CoreDevice UUID `1AD4F755-6F58-58E5-AC71-B1EDFECADA93`, Xcode 27.0 build `27A266a`, and iOS SDK 27.0. The synthetic app is `com.coryparry.IntentLabFixture`; test runner is `com.coryparry.IntentLabFixtureV2UITests.xctrunner` / `IntentLabFixtureV2UITests-Runner`. The run exited 65 before test-bundle load because `AppIntentsTesting` required missing `AppIntentsServices` symbol `RunnerServiceDispatcher.resolveValue`; no scenario dispatch or Siri attempt occurred.
- That checkpoint records the Intents lease released, `runnerAbsent: true`, and `sharedCampaignsAfterExit: 0`, based on post-run device inventory. It does **not** establish that the fixture app was removed or that its installed bytes match the staged payload. Earlier `physical-fixture-preparation-1.json` says preparation signed the app and runner but neither installed nor launched them at that checkpoint.

## Limits and unknowns

No package was installed, no MCP config/global tool was changed, and no simulator or physical-device session was opened. I did not verify release asset hashes, mobilecli's exact Device Kit payload/provisioning implementation for the pinned mobile-mcp release, whether the current device has a suitable profile, current installed-app inventory, or whether Mobile MCP's runner can coexist safely with the existing Intents ownership/release protocol. Those gaps make a same-device trial unjustified on this evidence.

- Default selection matches the explicit device ID. On the first simulator selection it calls `agent status`, then **automatically calls `agent install` when status fails**. Even ordinary screen inspection can therefore prepare another controller; this is not an approval-preserving replacement for the pending native provider.
- The wrapper resolves platform-scoped mobilecli binaries from its installed dependencies; legacy `go-ios` source remains present but is selected only by the explicit legacy robot mode. Its lock pins mobilewright/core 0.0.63 and Darwin arm64 mobilecli 1.0.17 (`sha512-lGgEsKs2hEEh924Cd9enRJUVg6fF8Yr9nTo44bvaYfzywsmoarAyFKHZQKrpTLrjV7WhhSU4j3R0MO6VgZoKIg==`). The repository manifest still says `0.0.1`; release-tag source is not proof of the exact published npm tarball bytes or release stamping.
- Stdio SIGINT/SIGTERM handlers call `process.exit(0)` without a runner release receipt or independently verified device absence in this wrapper. Exact selected app/process identity, exclusive ownership and Intents-style cleanup facts are not established by its generic tool success. Mobilecli's binary/helper internals and offline agent preparation remain unqualified here.
- No installation, agent preparation, device session or global configuration change occurred. The decision remains development-only evaluation at most, with separate authorization for any helper/device preparation. No shipped dependency was changed.
